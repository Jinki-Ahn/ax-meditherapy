## 스코프 원칙 (기획서 질문 2)

"이 의사결정(누구에게 얼마를)에 필요한 엔티티만" — 4개 엔티티로 닫는다. 모든 SNS 데이터를 담지 않는다.

**의도적으로 온톨로지 밖에 둔 것** (파이프라인 운영 상태로 취급):

- 실험 배치(batch), 처치/대조 배정표 — 파이프라인 ②의 출력물
- 추적 코드 — 배정(크리에이터×커뮤니티×제품 조합)에 종속된 운영 데이터
- 브리프 문서 — 파이프라인 ③의 출력물. 핵심 메시지와 커뮤니티 맥락의 결합(claim × community)도 이 시점에 생성
- **조합 스코어(크리에이터×커뮤니티×제품)** — 기획서 ⑤의 밴딧이 갱신하는 대상. 회전마다 생성·소멸하므로 루프 상태 파일에 둔다. 온톨로지의 `prior_score`는 조합 스코어의 출발값(사전 믿음)일 뿐, 주간 루프가 직접 갱신하지 않는다

이유: 온톨로지는 "세계가 어떻게 생겼는가"(불변에 가까운 구조), 배치·코드·브리프는 "이번 주에 무엇을 했는가"(회전마다 생성·소멸). 섞으면 슬롯 교체(멀티브랜드 확장) 때 갈아엎어야 한다.

## 엔티티 ↔ 기획서 대응

| 엔티티 | 기획서 근거 | 3층 스택 대응 |
|---|---|---|
| `community` (+`touchpoints`) | 질문 1 "커뮤니티(단위·밀도)", 3층 스택 2·3층 | 2층(측정 단위=부대) + 3층(처치 접점=PX 지점) |
| `creator` | 질문 1 "크리에이터(유형·도달)", 3층 스택 1층 | 1층(시딩 대상, 시차 실험) |
| `product` | 질문 3 ① "제품(핵심 메시지·소모 주기)" | — |
| `conversion_signal` | 질문 1 "전환 신호(검색·코드·재구매)", 질문 3 ④⑤ 2층 신호·이중 루프 | — |

## 필드 근거 분류

### A. 기획서에 직접 근거 있음

- `community.wom_density`, `measurement_unit` — "커뮤니티(단위·밀도)"
- `community.touchpoints.pair_group` — 질문 3 ② "유사 지점을 쌍으로 묶어 처치/대조 배정"
- `community.post_exit_channel` — 질문 2 "전역 후 쿠팡 재구매로 LTV 추적"
- `community.contamination_risk` — 질문 3 말미 "대조군 오염" 시 판단 불가 보고
- `creator.creator_type`, `reach_scope=national → 시차 식별` — 질문 1 1층 정의
- `creator.commercially_eligible` — "현역 장병은 영리 활동 금지라 시딩 불가"
- `product.consumption_cycle_days` — 질문 3 ① "소모 주기는 재구매 신호를 언제 기다릴지 정하는 제품 속성"
- `product.appeal_points`, `forbidden_claims` — 질문 3 ③ 브리프(핵심 메시지, 금지 표현)
- `conversion_signal.phase(leading/lagging)`, `window`, `weight`, `predictive_validity` — 질문 3 ④⑤ 선행/후행 신호·이중 루프의 가중치 보정
- `conversion_signal.min_sample` — 질문 3 ② "검정력 부족 설계 거부" + 말미 "신호 미달 시 판단 불가"
- 스키마 카테고리 중립(slot_type·category 개방형) — 질문 3 ① "스킨케어 필드를 헤어·향수로 교체 가능"
- `*.prior_score` — 질문 3 ① "현재 스코어"에서 출발했으나, 기획서 ⑤의 갱신 대상은 조합 스코어이므로 v0.2에서 '사전 믿음'으로 강등(아래 판정 참조)

### B. 추가 제안과 판정 (v0.2에서 확정)

기획서에 명시가 없던 추가 제안 6건을 별도 검증 AI가 기획서 대조 심사하고, 의견필요 항목은 기획자가 확정했다.

| # | 추가 항목 | 판정 | 결과 |
|---|---|---|---|
| 1 | `creator.audience_overlap` (커뮤니티 겹침 추정) | 의견필요 → **기획자: 제거** | 기획서 질문 1은 "부대별 타겟 불가 → 시차로만 식별"이라 명시. 겹침 가중치는 기획서가 불가능하다고 한 부대별 차등 노출을 식별 가정으로 재도입하는 확장이라 삭제. 시차(pre/post) 식별만 사용 |
| 2 | `community.closure_level` (닫힘 수치화) | 의견필요 → **기획자: 통합** | `contamination_risk` 하나로 통합(구조적 새는 정도 + 운영 중 오염). 같은 결정(검정력·판단 불가)에 두 필드를 먹이는 중복 제거 — '버리는 능력' 원칙 |
| 3 | `touchpoint.carried_product_ids` (v0.2까지 `carries_product` 불리언) | **정합 — 승인** | "입점을 전제하지 않는다"(기획서 한계)에서 필연 도출. 미취급 지점(빈 배열)은 검색·코드만 측정. v0.3에서 불리언→제품 ID 참조로 승격(단일 제품 가정 제거) |
| 4 | `touchpoint.weekly_traffic` | **정합 — 승인** | 명명된 신호 'PX 셀스루'를 비율로 재기 위한 분모 |
| 5 | `creator.avg_views` | **정합 — 승인** | '도달'의 실측치. 조회수를 KPI가 아니라 도달 지표로만 쓰므로 기획서의 KPI 전환 논지와 무충돌 |
| 6 | `appeal_points[].context` (커뮤니티 맥락) | **충돌 — 제거** | 제품 엔티티에 군 특정 상황을 박으면 카테고리 중립(슬롯 교체=멀티브랜드) 핵심 주장과 충돌. claim × community 결합은 브리프 생성 시점(파이프라인 ③)으로 이동 |

## 판정 및 확정 결정 (v0.1 → v0.2)

검증 AI의 즉시 수정 지적 2건 + 기획자 확정 3건:

1. **조합 스코어의 위치** (검증 AI 지적): 기획서 ⑤의 밴딧이 갱신하는 것은 조합(크리에이터×커뮤니티×제품) 스코어인데 v0.1은 개별 엔티티 `current_score`에 "주간 루프가 갱신"이라 적어 충돌. → 조합 스코어는 루프 상태 파일로, 엔티티 필드는 `prior_score`(사전 믿음)로 개명·강등.
2. **`appeal_points[].context` 제거** (검증 AI 지적 = B6): 위 표 참조.
3. **B1 제거, B2 통합** (기획자 확정): 위 표 참조.
4. **실험 배치는 엔티티로 승격하지 않음** (기획자 확정): 기획서 TODO가 "4개 엔티티"로 못박았고, 인과 설계의 심사 가시성은 온톨로지가 아니라 파이프라인 ② 산출물·리포트·README에서 보여준다. '버리는 능력' 스토리 유지.

## 평가 라운드 반영 (v0.2 → v0.3)

별도 평가 AI의 2관점 평가(심사위원/실무자 관점) 개선 제안을 심사해 반영 2건, 기각 2건:

**반영**

1. `product.required_disclosure` — 기획서 ③ "협찬 고지"가 스키마에 없던 누락. `forbidden_claims`(금지)와 짝을 이루는 의무 표기.
2. `creator.brand_safety_flags` — 시딩 불가·주의 사유를 `commercially_eligible` 불리언 하나로 뭉개지 않기 위한 사유 플래그.
3. `touchpoint.carries_product`(불리언) → `carried_product_ids`(제품 ID 참조) — "어떤 제품을 취급하나"를 표현 못 하던 단일 제품 가정 제거. 슬롯 교체(멀티브랜드) 주장의 실체 보강.

**기각 (사유 기록 — 본선 방어용)**

1. `creator.planned_publish_offset_days` 기각 — 게시 시점은 크리에이터 속성이 아니라 배치별 실험 설계의 출력(파이프라인 ②). 온톨로지에 넣으면 스코프 원칙(배치 상태 배제) 자기 위반.
2. creator↔community 도달 edge 기각 — 확정 결정 B1(audience_overlap 제거)의 부활. 기획서의 식별 전략은 "부대별 타겟 불가 → 게시 시차로만 식별"이며, 도달 관계를 온톨로지에 되살리면 이 식별 가정이 흔들린다.

**v0.4에서 해소**: 평가 제안 3번은 아래 리서치 결과에 따라 반영 완료.

## 데이터 획득 경로 리서치 (v0.3 → v0.4)

평가에서 최대 감점(실무자 관점 '데이터 획득 현실성' 10/25)이었던 "PX 셀스루를 실제로 어디서 구하나"를 별도 리서치 AI가 웹 사실확인. **평가 AI의 '사실상 불가' 판정은 과도한 비관으로 확인** — 결론은 "프록시로 근사 가능, 조건부 직접 확보 여지".

확인된 사실:

1. **PX는 위탁판매 구조** — 판매 후 수수료 공제 정산이므로 벤더는 정산 과정에서 **품목별 전국 판매량/판매액(월별)을 필연적으로 받는다** (확인됨).
2. **지점별 데이터는 국군복지단 내부에 존재** — 퇴출심사에서 "PX 상위 20개점 실적 합계"를 산출한 전례가 증거. 단 벤더에게 지점별로 상시 제공하는 제도·포털은 확인 불가 (협상 변수).
3. **발주는 부대(지점) 단위** — 관리관·PX병이 부대별 발주, 낮은 재고율로 발주≈판매에 근접 → **부대별 발주·재발주량이 지점 셀스루의 실무적 프록시** (부대 단위 발주 확인됨, 프록시 정밀도는 가정).
4. 공개 DB(공공데이터포털·국정감사)는 전국·품목 집계뿐, 지점별 없음.

스키마 반영:

- `conversion_signal.acquisition` (필수) — method/granularity/confidence(confirmed·proxy·negotiation_required)/fallback. **획득 경로를 못 적는 신호는 스키마 검증에서 거부** — "어떻게 채우나"를 온톨로지 수준에서 강제.
- `conversion_signal.control_definition` — measurement=treatment_vs_control_lift인 신호는 '대조'의 정의 필수 (조건부 required, 누락 시 검증 실패 확인).
- seed 반영: PX 셀스루 = 부대별 발주량 프록시(confidence=proxy) + 복지단 협의 리포트(fallback), 검색 리프트 = 지역·시차 조합 프록시, 추적 코드·리뷰 = confirmed.
